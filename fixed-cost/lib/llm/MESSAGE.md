# B8 추천 문장

`POST /api/message`의 기존 계약을 유지해요. 요청은 `{type, usage, service_name, params:{saving_monthly?,saving_yearly?,alt_name?}}`, 응답은 `{message,source:'ai'|'fallback'}`예요. B6 기본 문장과 fillPlaceholders, B4 callJson을 재사용해요. B1~B7의 공유 타입·스키마·규칙은 변경하지 않아요.

모델은 숫자 없는 문장 틀만 선택해요. 원문 서비스명·금액·혜택 설명·결제 원문·프로필을 모델에 보내지 않고 자리 표시만 전달해요. 빈 문장·120자 초과·숫자(전각 등도 포함)·알 수 없거나 깨진 자리 표시·잘못된 JSON은 버려요. 숫자와 자리 표시 검증만으로는 "인증 없이 무료" 같은 허구의 사실을 막을 수 없어, 종류별 승인된 문장 틀 안에서만 선택하도록 추가 검증해요. 따라서 표현 다양성은 제한적이에요. AI 실패·키 없음·타임아웃은 기존 기본 문장과 source=fallback으로 반환해요.

금액은 코드가 천 단위 쉼표로 치환해요. 월 금액만 있으면 연 금액을 열두 배로 계산하고, 서로 모순되거나 음수·소수·안전 범위를 넘는 금액은 400으로 거부해요. 필요한 금액·대안 이름이 누락되면 영 원이나 임의 이름으로 채우지 않아요. keep은 절약액 영 원만 허용해요. 120자 제한은 치환 전 틀의 길이이며 긴 확인된 이름으로 치환한 최종 문장은 더 길 수 있어요.

## B6·B7 연결과 신뢰 경계

서버용 buildRecommendationMessages는 기존 buildSuggestions에 확인된 구독·B7 판정·카탈로그를 전달한 뒤, 선택된 제안의 계산 금액과 카탈로그 표시 내용만 문장 생성에 사용해요. 제안 ID의 내부 형식을 파싱하지 않고 혜택별 B6 출력과 ID를 비교해 연결해요. 미확정 서비스, no/unknown 판정, null 가격, 모순 판정은 B6 규칙을 그대로 따르고 B8이 새 제안을 만들지 않아요. 제안의 source_url/checked_at/stale 등 기존 메타데이터를 유지해요.

기존 HTTP 계약에는 subscription ID나 benefit/result ID가 없어요. 따라서 /api/message 자체는 문장 표시 기능이며 호출자가 전달한 금액의 B6 계산 출처나 B7 적격 판정을 서버가 증명할 수 없어요. 입력 검증은 출처 인증이 아니에요. 실제 제안 연결에는 buildRecommendationMessages를 사용하고 임의 메시지 API 응답을 혜택 검증 결과로 취급하지 않아야 해요. API 증빙 연결이 필요하면 후속 계약 PR에서 제안 토큰/검증 결과 참조를 추가해야 해요. 프론트엔드는 이번에 수정하지 않았어요.

본문은 실제 UTF-8 20KB, 요청은 분당 공유 20회예요. 새 자유 텍스트·출처 필드는 거부해요. 본문·응답·오류 원문을 기록하지 않아요. API 키가 없어도 모든 테스트가 Mock으로 실행돼요.

## 자동 탐색 상태

혜택 자동 검색·수집·검증은 아직 없어요. B7은 이미 등록된 혜택의 자격만 판단하고 B8은 이미 계산된 제안의 표현만 처리해요. 사용자가 혜택을 직접 수집해야 하는 제품을 목표로 삼지 않아요. 시스템 자동 탐색이라는 추가 핵심 요구사항은 B9 전에 별도 B8.5로 개발할 계획이며 이번에는 구현하지 않았어요. 필요한 인터페이스와 변경 범위는 BENEFIT-DISCOVERY-PLAN.md에 제안으로만 적었어요.

재현: `node node_modules/tsx/dist/cli.mjs tests/examples/message.ts`. Mock 문장만 사용하며 실제 유료 모델·검색 API·Syntitan을 호출하지 않아요.
